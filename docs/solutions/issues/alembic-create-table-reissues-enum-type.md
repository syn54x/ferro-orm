## Problem

Two models share one `StrEnum`. `Category` was migrated earlier, so the
Postgres type `categorycolor` is live. A later revision adds `Card` with
the same enum. Autogenerate renders:

```python
op.create_table('card',
sa.Column('color', sa.Enum('rust', 'amber', name='categorycolor'), nullable=True),
...
```

and `alembic upgrade head` dies:

```text
psycopg.errors.DuplicateObject: type "categorycolor" already exists
[SQL: CREATE TYPE categorycolor AS ENUM ('rust', 'amber')]
```

The same thing happens to a type `connect(auto_migrate=True)` created before
the project switched to Alembic, and when an enum column is *moved* to a new
table (`drop_column` + `create_table`) in one revision.

## Cause

Alembic's `create_table` implementation fires SQLAlchemy's `before_create`
with `checkfirst=False`. A `sa.Enum` adapts to a native `postgresql.ENUM`
whose `create_type` defaults to `True`, so `_on_table_create` issues
`CREATE TYPE` unconditionally. Nothing in Alembic knows whether the type
already exists; the upstream answer (alembic#278) is to hand-edit the column
to `postgresql.ENUM(..., create_type=False)`.

Two things made the fix non-obvious:

- **`add_column` is not affected.** Alembic's `add_column` never creates a
  type (it fails with `UndefinedObject` when the type is missing), so only
  `create_table` columns need the flag.
- **`repr()` drops the flag.** `sqltypes.Enum.__repr__` inspects only
  `Enum` and `SchemaType` constructor arguments, so
  `repr(postgresql.ENUM(..., create_type=False))` is
  `ENUM('rust', 'amber', name='categorycolor')`. Alembic's default type
  renderer *is* that `repr`, so swapping the column's type in the op still
  writes a type-creating column into the file.

## The fix

The provenance decision that already drives the downgrade (#438,
ADR-0020) has an exact complement: a type with an added column that is
*not* introduced is **reused**. `enum_types_reused_by_revision` in
ferro-ddl-lowering returns it; `_plan_enum_type_provenance` returns both
halves over FFI. The comparator replaces each `create_table` column of a
reused type with a copy carrying `column.type.adapt(postgresql.ENUM,
create_type=False)`, and the bridge's `render_item` hook (wired in
`env.py`) renders the flag Alembic cannot. Before rewriting, the comparator
calls the context's `render_item` on the new type and raises with the line
to add when the result lacks the flag, so an unwired `env.py` fails at
generation, not at upgrade. ADR-0021 records the decision and the
alternatives.

## How to recognize

- `DuplicateObject: type "<enum>" already exists` from an autogenerated
  `upgrade()` whose `create_table` carries `sa.Enum(..., name='<enum>')` and
  another live table already has a column of that type.
- A rendered `postgresql.ENUM(...)` column with **no** `create_type=False`
  when you expected one: the renderer ran without `render_item`. In tests,
  `render_python_code` builds its own `AutogenContext` — pass
  `render_item=` explicitly (`_render_ops` in
  `tests/test_row_security_alembic.py` does).
- `CreateTableOp.columns` holds the table's constraints too; anything that
  walks it for columns must `isinstance(..., sa.Column)` first.
