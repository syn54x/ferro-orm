# One migration renders its DDL once per target dialect, and only for the dialects a project targets

A DDL step is SQL, and ferro's SQL differs by dialect: column types, the standalone unique index, native enum types, row security and SQLite's table rebuilds have no cross-dialect spelling. Tools that store SQL keep one migration chain per database (Flyway's per-vendor locations, Diesel's per-backend directories, Prisma's provider-bound history); tools that store operations render them per backend at apply time and grow escape hatches where the backends diverge (Django's `connection.vendor` gates, Liquibase's `dbms=`). We decided that a migration stays **one directory** — one number, one `ir.json`, dialect-neutral data steps — and that each DDL step carries **one rendering per target dialect**, all written in the same generator run from the same planner output, so a project that tests on SQLite and ships on Postgres has one chain whose two renderings can never drift apart. The generator renders **only the dialects the project targets**, declared in committed configuration per database alias (defaulting to the single dialect the generate-time URL implies, refusing with the line to add when nothing resolves); a Postgres-only team never sees a SQLite file. The runner picks the rendering by the connection's dialect and refuses, naming the fix, when a migration has none for it. How the renderings are laid out inside the directory is the CLI's call.

Amended by ADR-0036: target dialects are declared per *database* (the word that replaces "database alias"), and the URL-implied default is gone. `dialects` is required; `migrate new` without it refuses and prints the line to add, so the generator reads no URL.

## Considered options

- **One chain per dialect** (the SQL-tool norm). Rejected: two chains share nothing, so their numbers, snapshots and data steps drift; ferro's generator can write both from one plan and keep them in lockstep, which no SQL-storing tool can.
- **Store planner operations and render at apply time** (the Django/Alembic shape). Rejected: the reviewed artifact would no longer be the SQL that runs, which is the reason the in-house system writes SQL at all, and SQLite's rebuilds and Postgres's `CONCURRENTLY` steps would need per-dialect escape hatches inside the neutral file anyway.
- **Render every dialect ferro supports, always.** Rejected: doubles review load for every team that targets one database, for files they can never run.
